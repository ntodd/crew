# Crew Linux job VMs on bare-metal KVM

Measured November 18, 2026. On this host and short SQLite job, Cloud Hypervisor finished a single live GitHub job 12% faster than Firecracker. When four VMs launched together, its median job finished 14% later. Both tests used the same guest kernel and filesystem.

## How the comparison ran

A physical AMD Ryzen 9 9950X (16 cores, 32 threads, 123 GiB RAM) ran Ubuntu 24.04.5 LTS with host kernel 7.0.0-38-generic and KVM. Firecracker 1.17.0 and Cloud Hypervisor 54.1 each launched fresh x86-64 VMs on that host. Each VM got two vCPUs, 2,133 MiB of guest RAM (Crew's 2,048 MiB job size plus its boot allowance), a 6 GiB sparse ext4 disk, and one TAP device. The host restricted each VMM and its monitor to two distinct physical cores. The four slots used disjoint CPU sets (4–5, 6–7, 8–9, and 10–11). Other host services, including Foreman, stayed running. The benchmark did not generate a concurrent Foreman workload. Timers started immediately before VMM process launch, after staging and reading the private disk copy to warm the host page cache.

Both VMMs booted the same Linux 6.18.60 ELF kernel with Crew's PVH-enabled x64 configuration. Both used copies of the same Crew v0.2.0 root filesystem with Docker 29.9.2, Actions runner 2.338.2, and the benchmark files added. The job compiled SQLite 3.54.1 from its amalgamated C source with GCC at `-O0 -DSQLITE_THREADSAFE=0`, created a file-backed database, inserted the integers 1 through 250,000 in a transaction, and checked that their sum was 31,250,125,000. Each run started with a fresh disk.

- **GitHub trials.** Each job had a unique runner label. GitHub showed the job queued before the VMM started. Crew's guest service started Docker, retrieved a single-use JIT configuration from the benchmark controller, and ran the real Actions listener. The controller timestamped the listener's ready, job-started, and job-finished events on the host monotonic clock. The workflow also marked the beginning and end of the SQLite step. GitHub's API independently confirmed the assigned runner and successful job conclusion. The time to mint a JIT configuration is outside the timer. The time for the guest to fetch it and connect to GitHub is inside.
- **Offline trials.** Crew's guest conformance mode started Docker, checked `docker info` and the runner binary version, then ran the same SQLite compilation and test as the runner user. Readiness here means those checks finished. Completion means the test returned success. This removes GitHub scheduling and network latency from the workload.
- **Memory.** Each job ran in a fresh cgroup v2 with a 4 GiB limit. Peak host memory is its `memory.peak` at the end of the measurement. It includes touched guest memory, VMM and monitor memory, and kernel or file-cache charges accounted to that cgroup. It excludes the shared controller and the disk copy warmed before launch. The raw data also includes the VMM process's peak RSS.
- **Pairing.** One trial started a single VM or released four VMs together. Firecracker and Cloud Hypervisor ran consecutively, with their order reversed across rounds. There were six measured rounds offline and four with GitHub at each concurrency. Per-VM medians pool the four slots for burst trials. For last-job timing, each burst contributes one observation. The two offline warm-ups and one live pilot are in the raw data and excluded from all reported medians.

The harness launched both VMMs directly in containers using the physical host's KVM device. The benchmark covered guest boot, runner connectivity and job execution. Production Crew scheduling, systemd unit setup, image download or cloning, VM teardown, cold host cache, and sustained builds fall outside these timings. The production systemd unit applies a CPU quota and memory limit. This experiment used fixed CPU sets and a common 4 GiB cgroup limit for both VMMs.

## Why four concurrent Cloud Hypervisor jobs slowed down

The host spent time compacting physical memory for transparent huge pages as newly booted VMs touched guest RAM. On this machine, disabling Cloud Hypervisor’s per-VM request for transparent huge pages recovered the first-compile performance in all four paired bursts. Elapsed times below are medians across individual VMs. The Firecracker reference consists of two baseline bursts from the same profiling session.

| Four fresh VMs | Bursts | First compile | Launch through first SQL check | Memory stalls during first compile |
| --- | ---: | ---: | ---: | ---: |
| Cloud Hypervisor default | 4 | 3.80 s | 7.10 s | 0.463 s |
| Cloud Hypervisor with `memory.thp=false` | 4 | 2.96 s | 5.43 s | 0.000 s |
| Firecracker reference | 2 | 2.98 s | 5.88 s | 0.000 s |

The host used `madvise` for both transparent huge pages and defragmentation, with a 2 MiB huge-page size. Cloud Hypervisor 54.1 requests transparent huge pages for guest RAM by default. Linux can synchronously reclaim and compact memory on this allocation path. Crew can control the request through Cloud Hypervisor's per-VM `memory.thp` field. [Cloud Hypervisor memory mapping](https://github.com/cloud-hypervisor/cloud-hypervisor/blob/v54.1/vmm/src/memory_manager.rs) · [Linux transparent huge pages](https://docs.kernel.org/admin-guide/mm/transhuge.html)

Two confirmation bursts per setting also recorded the host-wide `compact_stall` counter. During individual VMs' overlapping first-compile windows its increase ranged from 1,570–1,975 with default Cloud Hypervisor and 0 with the override. Each observation includes all four jobs and other host activity, so they cannot be summed. Per-cgroup memory stalls in the table use the increase in `memory.pressure` (the `some` total). The median CPU-only integer loop took 0.37 s with default Cloud Hypervisor and 0.37 s with the override. Across the two single-VM confirmation pairs, median launch through the first SQL check took 4.73 s with defaults and 5.09 s with the override.

The diagnostic ran offline on the same host with the same VMM binaries, kernel configuration, VM size, CPU assignments and SQL workload. It added guest timing around GCC and SQL, then repeated the compilation and ran the CPU-only loop. Host counters were sampled at guest phase boundaries, with up to roughly one polling interval (50 ms) of timing uncertainty. Rounds 3–6 compare the default and the override at four-way concurrency, reversing their order in two of the rounds. All settings were local to the temporary benchmark VMs. The GitHub workflow timings earlier in this report apply to the original defaults.
