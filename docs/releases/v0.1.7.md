# Crew 0.1.7

Crew now tells you when a job's size is wrong, and how many minutes the
fleet spends on jobs. Job pages, repo pages and a new Right-sizing page
suggest a smaller, larger or faster size from each job's recent runs. A
new Usage page adds up job and VM minutes by day.

## What changed

- **Right-sizing hints.** A finished job's page suggests a size from its
  last 10 runs on the same shape. A single run is enough to ask for a
  larger size: after an OOM kill, when most runs stall on memory, or
  when one peaks at 90% of its memory. Every other hint waits for 5
  complete successful runs. It goes faster when at least 3 runs, and at
  least half of them, waited on a CPU a quarter of the time or more, and
  a size with more vCPUs fits. It goes smaller to the allowed size with
  the least memory that still holds the highest peak and disk use, plus
  25%, without slowing any run by more than 5% by estimate. When no
  allowed size fits well, it names a custom shape, and admins get a link
  to Sizes & labels. The repo page lists its jobs' hints, and when a
  job's recent runs used more than one size, the job page shows its
  median time on each. The hints are display only: nothing changes
  placement, labels or sizes.
- **A Right-sizing page** (`/sizing`) adds the hints up across the
  fleet over the last 7 days: the memory runs reserved and the most
  they used, in GiB-hours, what applying every hint would free or take,
  each repo's share, and every hint, largest saving first.
- **A Usage page** (`/usage`) shows job minutes (with the rounded-up
  count GitHub would bill), VM minutes split into boot, idle, busy and
  teardown, and reserved GiB-hours and vCPU-hours, over 7, 30 or 90
  days, by box, repo and size. Box and repo pages get a 30-day usage
  panel, and the dashboard counts today's job minutes. Closed UTC days
  are rolled up hourly, at :53, and kept for good. Members see the whole
  fleet's and every box's usage, with the repos they can't read added up
  into one unnamed row, and the dashboard's count includes every repo.
  The Right-sizing page only covers repos the viewer can read.
- **The guest reports memory peaks, OOM kills and pressure.** crew-guest
  reads memory every second and sends the highest use since its last
  post, the kernel's OOM kill count, and CPU and memory stall (PSI).
  `jobs.oom` is now set when a process was killed for memory.
- **Network rates.** `vm.metrics` always sent 0 for the network rates,
  so `vm_metrics`' network columns and `jobs.net_bytes` were always 0.
  The agent now works them out from the guest's byte counters.
- **A job's resource summary only counts its run.** It used every
  sample the VM sent, boot and waiting for the job included, so average
  CPU came out low on short jobs. It now counts the samples from the
  job's start to just past its end. A fast job whose VM was linked
  after its `completed` webhook used to get no summary at all; it gets
  one now, and it's written again once the VM is gone and every sample
  is in.

## Before you install it

- Three migrations run on start: five nullable columns on `vm_metrics`;
  seven nullable columns on `jobs`, and an index on (`repo_id`,
  `workflow_name`, `name`, `completed_at`); and three new tables for
  usage. Jobs aren't pruned, so the index takes as long to build as the
  table is big.
- Update the control plane before the boxes, as usual. An older control
  plane refuses a `vm.metrics` with the new fields and logs a warning,
  so it would drop those samples.
- The memory peaks, OOM kills and pressure come from the 0.1.7 guest
  image. Hints only count runs from it, so a job needs runs on the new
  image before it gets a hint, and 5 complete successful ones before any
  hint but a larger size. Network rates only need the agent update.
- The first usage rollups backfill history, 31 days an hour, back to the
  first VM or job. A box's online time comes from its samples, which are
  kept for 7 days, so older days don't have it. What a box offers is
  recorded as of the rollup, so backfilled days show its current
  capacity.
- The hardware checks in `docs/releasing.md` weren't run for this
  release.
