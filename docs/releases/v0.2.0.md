# Crew 0.2.0

Background jobs can now run on room regular jobs aren't using, Crew can
start workflows on time instead of waiting on GitHub's scheduler, and the
right-sizing hints turn into work: an issue to file, a size to add, and a
check on whether the change helped. The repo page is now about the repo's
CI.

## What changed

### Spare capacity

- **`-spare` labels.** `runs-on: crew-<size>-spare` asks for spare
  capacity, for work like flake hunts, mutation testing and long fuzz
  runs. `crew-spare`, `crew-<arch>-spare` and `crew-<size>-<arch>-spare`
  work too. Every regular job in a placement pass is tried before any
  spare one, and a box's spare VMs stay within its spare share: 50% of
  its memory, vCPUs and VM slots unless you set another. A spare VM never
  takes a box that a regular job looked for in the same pass and couldn't
  get. Running spare jobs aren't preempted, so a regular job can still
  wait on one that's already going.
- The queue, dashboard, box, job and repo pages tag spare jobs. The box
  page has a "Spare share (%)" override, and the label tester on Sizes &
  labels says which boxes' spare shares could hold a spare label.
- New sizes can't be named `spare` or end in `-spare`. A size named that
  way before keeps working, and Sizes & labels says to rename it to use
  `crew-…-spare`.

### Workflow schedules

- **Crew can start a workflow on a cron.** GitHub has been running
  `schedule:` triggers 6 to 10 hours late. An admin adds a schedule on
  the repo page (a workflow file, a ref and a five-field cron in UTC),
  and Crew dispatches it within the minute. A tick missed in a short
  outage still fires, but a match more than an hour old waits for the
  next one, so a night job doesn't run in the afternoon. Each schedule
  has Run now, Disable and Remove, and a dispatch GitHub refuses shows
  its error on the page. Changes and manual runs are audit-logged.

### The repo page

- **It's built around the repo's CI now,** over 7 or 30 days: jobs run,
  pass rate, run time and queue wait (p50 and p95), job minutes and flaky
  jobs; charts of jobs and run time per day; every workflow's jobs; flaky
  jobs (failed, then passed on a re-run of the same commit); and recent
  runs. Settings, schedules and the `runs-on` snippets moved to a rail.
- **Cache misses.** Install and fetch steps whose cache never seems to
  hit (`mix deps.get`, `npm ci`, `setup-*` actions, cache post steps and
  the like) are flagged on the job page and listed on the repo page,
  going by the job's last 10 successful runs.

### Right-sizing

- **More vCPUs only on the critical path.** A job that waits on its CPUs
  is only told to grow when it's on its run's critical path, which Crew
  works out from job times. Off the path, more vCPUs would take capacity
  without finishing the run sooner, and the hint says so.
- **File an issue from a hint.** A hint with a size to move to has File
  issue, which opens GitHub's new-issue form on the repo with the
  `runs-on` change, the workflow file, the reasons and a link back to the
  job filled in. Copy as Markdown copies the same for other trackers. The
  repo page and the By repo table on `/sizing` can file one issue for
  all of a repo's hints, as a checklist grouped by workflow file. The
  person who clicks files it, so the App needs no new permission.
- **The workflow file.** Crew keeps each run's workflow file, and a hint
  links it next to its `runs-on` line.
- **The `runs-on` line keeps the job's tier and labels.** It used to drop
  `-spare`. It now swaps only the Crew label, so `[self-hosted,
  crew-m-spare]` becomes `[self-hosted, crew-xs-spare]`.
- **Dismiss a hint.** Admins can dismiss a hint nobody will apply, with a
  reason. It leaves `/sizing`'s totals and the issues, and comes back if
  the job changes size or the hint changes kind. Dismissed hints are
  listed apart, with who dismissed them, when and why, and Restore. Both
  are audit-logged.
- **Custom sizes in one step.** A custom hint's link opens Sizes & labels
  with its shape filled in, and offers to allow the new size for the
  job's repo when that repo limits its sizes. `/sizing` groups the custom
  hints by shape, so one size can serve several jobs. Once the size
  exists, the hint becomes "Try <name>" with its own issue link.
- **Did it help?** `/sizing` lists the jobs that moved to a new size in
  the last 30 days: their median time on each size, what the move freed
  over the week, and a flag when the new size is more than 5% slower or a
  run on it ran out of memory.

### Fixes

- **Job retention.** `CREW_JOB_RETENTION_DAYS` (default 90) was read and
  never used. An hourly job now prunes jobs, run attempts and destroyed
  VMs past it, a whole run at a time. Usage totals are kept.
- **Job minutes** counted jobs that were cancelled while still queued,
  their whole wait included. They're left out now.
- **VM servers.** Four VM server crashes within 5 seconds, from any VMs,
  ended every VM's server until the control plane restarted. The restart
  budget now covers a box's worth of VMs.
- **Runners killed mid-job.** A control plane restart, or a box
  disconnecting, failed a VM that was still `requested` straight away. A
  runner that had just registered and taken a job could be force-stopped
  with the job on it. Both now delete the runner first, and keep the VM
  if its runner has a job. A finished VM with no job now takes the job
  GitHub names for it. All three came out of a Quint model of the VM
  lifecycle (`models/`), which the tests replay against
  `Crew.VMs.Machine`.
- **The agent** answered `ok` to a repeated `vm.start` for a VM that had
  already exited. It answers `duplicate` now.

## Before you install it

- Seven migrations run on start:
  - `jobs.spare` and `vms.spare` (booleans, default false) and
    `boxes.spare_pct` (nullable; empty means 50);
  - the `schedules` and `sizing_dismissals` tables;
  - `run_attempts.workflow_path` (nullable) and an index on
    `run_attempts(updated_at)`;
  - a data migration that forgets the usage days from the last week that
    had a job cancelled while queued. Those days show as pending on the
    Usage page until the rollup at :53.
- `CREW_JOB_RETENTION_DAYS` now deletes. At the default of 90 days
  nothing goes yet, since no install has that much history. Set it higher
  if you want to keep more.
- A schedule needs a `workflow_dispatch:` trigger on its workflow. Drop
  the workflow's `schedule:` so GitHub doesn't start it again hours
  later.
- Hints link the workflow file for runs from after the update. Runs that
  were still going pick it up from their next event; finished ones don't
  get a link.
- Update the control plane before the boxes, as usual.
- The hardware checks in `docs/releasing.md` weren't run for this
  release.
